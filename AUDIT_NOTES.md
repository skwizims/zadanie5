# Технический аудит перед публикацией

Этот файл — рабочая заметка по проверенному архиву. Он не является частью требований задания и при желании может храниться вне публичного репозитория.

## Что исправлено в этой копии

- README переписан по фактическим классам, endpoint и настройкам из исходников.
- Удалён устаревший `README.txt`, чтобы не было двух конкурирующих документов; основная документация теперь `README.md`.
- Приведено к единому форматированию несколько наиболее сжатых Java-файлов: `JwtAuthenticationFilter`, `OpaqueTokenStore`, `OpaqueTokenService`, `SessionStatus`, `UserSessionRepository`.
- Изменения форматирования не должны менять поведение программы.

## Проверенные несоответствия и замечания

### 1. Настройки БД не совпадают

`application.yaml` использует `service_user` / `service_pass`, а `docker-compose.yml` создаёт `app_user` / `app_password`. Перед запуском контейнера нужно согласовать значения. Если PostgreSQL уже инициализирован в volume, изменение переменных окружения может быть недостаточным.

### 2. Старый README был неактуален

Старый файл описывал HTTP Basic, CSRF endpoint `/api/auth/csrf` и регистрацию `/api/auth/register`. Фактический контроллер аутентификации использует `/auth/register`, `/auth/login`, `/auth/refresh`; HTTP Basic отключён.

### 3. CSRF

В `SecurityConfig` CSRF использует `CookieCsrfTokenRepository`, но запросы `/auth/**` и `/api/auth/**` исключены из CSRF-проверки. Поэтому README не должен утверждать, что CSRF-токен обязателен для всех POST/PATCH/DELETE запросов.

### 4. Opaque-токены

`OpaqueTokenService` и `OpaqueTokenStore` используются в `TokenPerformanceTest`, а не в основном потоке аутентификации. README теперь описывает это различие.

### 5. Benchmark

`TokenPerformanceTest` — простое измерение времени одного прохода фиксированного числа итераций. Оно не выполняет отдельный прогрев JVM и не считает статистику по нескольким независимым запускам. Это допустимо как учебная демонстрация, но результаты не следует представлять как строгий сравнительный benchmark.

### 6. Фильтр JWT

`JwtAuthenticationFilter` проверяет access JWT и загружает пользователя. Исключение при проверке токена очищает SecurityContext, после чего запрос продолжает проходить через цепочку фильтров и будет обработан правилами авторизации.

### 7. Данные dev-профиля

`DataInitializer` создаёт тестовые учётные записи `admin` / `Admin1234` и `user` / `User1234`, если их нет. Не использовать эти реквизиты в публично доступной среде.

### 8. JWT-секрет

В конфигурации хранится учебный ключ, сформированный из имени согласно условию задания. Это требование учебной работы, но для публичного или производственного развёртывания секрет следует вынести из репозитория в переменную окружения. Убедитесь, что преподавателю доступна требуемая конфигурация в соответствии с формулировкой задания.

## Что необходимо сделать вручную перед сдачей

1. Заполнить ФИО и фактические дату/время в начале `README.md`.
2. Согласовать параметры PostgreSQL между `application.yaml` и `docker-compose.yml`.
3. На своей машине выполнить `./mvnw clean test` (Windows: `mvnw.cmd clean test`).
4. Запустить приложение и воспроизвести сценарий из коллекции `Задание 5 JWT.postman_collection.json`.
5. Убедиться в БД, что статусы после обновления и повторного предъявления старого refresh меняются на `USED` и `REVOKED`.
6. Проверить `git status` и убедиться, что в коммит не попадут `target/`, `.idea/`, локальные секреты и файлы IDE.

## Ограничения проверки

Сборка и интеграционное тестирование в окружении подготовки архива не подтверждены. Поэтому эта копия не содержит заявления, что тесты успешно прошли после изменений.
