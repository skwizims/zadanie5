# Utility Management System

## 1. Назначение проекта

Приложение предназначено для учёта коммунальных ресурсов. Оно позволяет работать с пользователями, помещениями, приборами учёта, показаниями счётчиков и начислениями.

Основные возможности:

- регистрация и аутентификация пользователей;
- разграничение доступа по ролям `ADMIN` и `USER`;
- управление пользователями, помещениями и приборами учёта;
- передача и подтверждение показаний;
- формирование и оплата начислений;
- передача помещения другому владельцу;
- получение отчёта по потреблению за период;
- выдача и обновление JWT-пары access/refresh с серверным учётом refresh-сессий.

## 5. Аутентификация и управление токенами

Аутентификация реализована через Spring Security и JWT. HTTP Basic и form login отключены.

### Endpoint аутентификации

Все запросы ниже отправляются на базовый адрес приложения, например `http://localhost:8080`.

| Метод | Endpoint | Назначение | Успешный статус |
|---|---|---|---|
| `POST` | `/auth/register` | Создать пользователя и выдать пару токенов | `201` |
| `POST` | `/auth/login` | Проверить логин/пароль и выдать пару токенов | `200` |
| `POST` | `/auth/refresh` | Обменять действующий refresh-токен на новую пару | `200` |

Пример тела запроса регистрации:

```json
{
  "username": "newuser",
  "password": "Password123",
  "fullName": "New User",
  "email": "newuser@example.com",
  "phone": "+10000000000",
  "deviceId": "postman"
}
```

Пример тела запроса входа:

```json
{
  "username": "user",
  "password": "User1234",
  "deviceId": "postman"
}
```

Пример тела запроса обновления:

```json
{
  "refreshToken": "<refresh-token>"
}
```

Успешный ответ содержит пару:

```json
{
  "accessToken": "<access-token>",
  "refreshToken": "<refresh-token>"
}
```

Для обращения к защищённым endpoint передавайте access-токен в заголовке:

```http
Authorization: Bearer <access-token>
```

Refresh-токен передаётся в JSON-теле запроса `/auth/refresh`; endpoint обновления не требует access-токен.

### Формат и проверка JWT

Оба токена являются JWT с подписью HS256. В токен включаются:

- `sub` — имя пользователя;
- `jti` — уникальный идентификатор токена;
- `type` — `access` или `refresh`;
- `iat` — время выпуска;
- `exp` — время истечения.

Сроки задаются в `application.yaml`:

| Настройка | Значение по умолчанию |
|---|---:|
| `app.jwt.access-seconds` | 900 секунд (15 минут) |
| `app.jwt.refresh-seconds` | 604800 секунд (7 дней) |

JWT-секрет задаётся свойством `app.jwt.secret-hex`. Для учебной работы значение в конфигурации сформировано из имени исполнителя в соответствии с условием задания. Не публикуйте реальные секреты в общедоступных репозиториях и не используйте учебный ключ в рабочей среде.

### Учёт refresh-сессий

Сессии сохраняются в таблице `user_sessions`. Одна строка соответствует одной выданной паре токенов.

В записи хранятся:

- UUID сессии;
- имя пользователя и необязательный `deviceId`;
- access- и refresh-токены;
- время истечения обоих токенов;
- статус сессии.

Возможные статусы `SessionStatus`:

| Статус | Значение |
|---|---|
| `ACTIVE` | Refresh-токен ещё не использован и не отозван |
| `USED` | Refresh-токен был успешно использован для обновления |
| `REVOKED` | Refresh-токен отозван после повторного предъявления |

При успешном обновлении старая запись сохраняется со статусом `USED`, а для новой пары создаётся отдельная запись `ACTIVE`. Поиск сессии для обновления выполняется с блокировкой записи в репозитории. Операция обновления выполняется в транзакции.

Повторное предъявление ранее использованного, ещё не истёкшего refresh-токена приводит к переводу соответствующей записи в `REVOKED` и отказу в выдаче новой пары.

### Коды ответов для ошибок аутентификации

| Ситуация | HTTP |
|---|---:|
| Неверные учётные данные | `401` |
| Отсутствующее или пустое обязательное поле | `400` |
| Неверный, просроченный или неподходящий refresh-токен | `401` |
| Неизвестная, использованная или отозванная refresh-сессия | `401` |
| Регистрация уже существующего пользователя | `409` |

## 6. Opaque-токены и сравнение производительности

В проекте отдельно реализованы:

- `OpaqueTokenService` — генерация случайного Opaque-токена с использованием `SecureRandom`;
- `OpaqueTokenStore` — объектное хранилище записей токенов на основе `ConcurrentHashMap`;
- `TokenPerformanceTest` — тестовое сравнение операций создания и проверки JWT и операций создания, сохранения и поиска Opaque-токена.

Тест печатает среднее время операции для заданного количества итераций. Это учебное измерение, а не полноценный статистический benchmark: результат зависит от JVM, прогрева, нагрузки и окружения. Для сравнимых результатов запускайте тесты в одинаковых условиях несколько раз.

## 8. Разграничение доступа

В `SecurityConfig` настроены следующие правила:

- endpoint `/auth/login`, `/auth/register`, `/auth/refresh` и endpoint получения CSRF доступны без аутентификации;
- операции создания, изменения и удаления пользователей, помещений и счётчиков ограничены ролью `ADMIN` (для `POST /api/users` установлен запрет);
- отправка показаний доступна ролям `USER` и `ADMIN`;
- подтверждение показаний доступно `ADMIN`;
- оплата начисления доступна `USER` и `ADMIN`;
- передача помещения и получение отчёта доступны `ADMIN`;
- остальные endpoint требуют аутентификации.

Дополнительные проверки принадлежности данных выполняются компонентом `SecurityChecks` и бизнес-логикой сервисов там, где они подключены.

## 9. Postman

В репозитории находятся коллекции:

- `Задание 5 JWT.postman_collection.json` — регистрация, вход, обновление токенов и повторное предъявление старого refresh-токена;
- `postman_collection.json` — основные запросы приложения;
- `Zadanie 3 API.postman_collection.json` — коллекция предыдущего этапа API.

Для коллекции задания №5 задайте переменную `baseUrl`, например:

```text
http://localhost:8080
```

Проверочный сценарий задания №5:

1. Выполнить `POST /auth/login` и сохранить access/refresh.
2. Вызвать защищённый endpoint с access в `Authorization: Bearer`.
3. Выполнить `POST /auth/refresh` с текущим refresh.
4. Убедиться, что получена новая пара, старая запись имеет статус `USED`, новая — `ACTIVE`.
5. Повторно отправить старый refresh и получить `401`.
6. Проверить, что старая запись получила статус `REVOKED`, а новая пара не была выдана.
